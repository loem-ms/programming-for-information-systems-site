### ផែនការគម្រោង (project charter) នៅសប្ដាហ៍ទី 9

កន្លះទំព័រ ដែលអ្នកសរសេរនៅក្នុងថ្នាក់។ វាជាផែនការរបស់អ្នក និងជាសេចក្ដីព្រាងដំបូងនៃរបាយការណ៍របស់អ្នក។

1. **តើនរណាប្រើប្រព័ន្ធរបស់ខ្ញុំ ហើយតើម្នាក់ៗត្រូវការអ្វី។** ឧទាហរណ៍ អ្នកសម្របសម្រួល អ្នកស្ម័គ្រចិត្ត អង្គការដៃគូ អ្នកបរិច្ចាគ ឬនរណាម្នាក់នៅក្នុងអាហារដ្ឋាន។
2. **ការសម្រេចចិត្តបីរបស់ខ្ញុំ រហូតមកដល់ពេលនេះ។** setting · តម្លៃរបស់ខ្ញុំ · ភស្តុតាងដែលខ្ញុំមាន (ឬដែលខ្ញុំនៅត្រូវការ)។
3. **ផ្នែកបន្ថែមរបស់ខ្ញុំ និងរបៀបដែលខ្ញុំនឹងសាកល្បងវា។** តេស្តពីរ៖ ធាតុចូល (input) និងចម្លើយដែលខ្ញុំរំពឹងទុក។
4. **គំនូរដំបូងនៃប្រព័ន្ធរបស់ខ្ញុំ។** មនុស្ស file និងរបៀបដែលទិន្នន័យហូររវាងពួកវា។ ខ្មៅដៃ និងក្រដាសក៏បាន។

## ផ្នែកទី 1 · វាដំណើរការ

- `bridge.check("all", folder="my_foodbridge")` បង្ហាញ ✅ សម្រាប់ផ្នែកដែលអ្នកបានសរសេរ ហើយគ្មានបញ្ហា file ⚠️ ទេ។
- `bridge.show("app", script=["1", "2", "3", "q"])` បង្ហាញថា menu របស់អ្នកដំណើរការ (ចូរបន្ថែម `"4"` ប្រសិនបើផ្នែកបន្ថែមរបស់អ្នកបានបន្ថែមជម្រើសមួយ)។
- ការ run `python app.py` នៅក្នុង terminal គឺជាជួរដេកបន្ថែមដ៏ល្អមួយ ក្នុងកំណត់ត្រាការផ្ទៀងផ្ទាត់របស់អ្នក (ផ្នែក សាកល្បងបន្ថែម (Go further) នៃសប្ដាហ៍ទី 9) ប៉ុន្តែវាមិនចាំបាច់ទេ។

### កំណត់ត្រាការសម្រេចចិត្ត (decision log)

ការសម្រេចចិត្តមួយ ជួរដេកមួយ នៅក្នុង `README.md` របស់អ្នក។ ទាំងនេះគឺជាជួរឈរនៃកំណត់ត្រាការសម្រេចចិត្តប្រចាំសប្ដាហ៍របស់អ្នក (*ជម្រើសរបស់ខ្ញុំ · ជម្រើសផ្សេង · មូលហេតុដែលខ្ញុំជ្រើស · ភស្តុតាង · អ្នកដែលរងផលប៉ះពាល់ / ផលប៉ះពាល់ទៅវិញទៅមក (trade-off)*) ដោយ *ជម្រើសរបស់ខ្ញុំ* ត្រូវបានបំបែកជាពីរ៖ setting និងតម្លៃរបស់វា។

## ផ្នែកទី 3 · ផ្នែកបន្ថែមរបស់ខ្ញុំ

ចូរជ្រើសផ្នែកបន្ថែម **មួយ** នៅសប្ដាហ៍ទី 8 ហើយរៀបចំវាក្នុងផែនការគម្រោងរបស់អ្នក នៅសប្ដាហ៍ទី 9។ អ្នកប្រហែលជាបានចាប់ផ្ដើមវារួចហើយ នៅក្នុងផ្នែក ⭐⭐ **សាកល្បងបន្ថែម (Go further)** នៃសប្ដាហ៍ណាមួយ។ វិធានមានដូចតទៅ៖

- វាស្ថិតនៅក្នុង file ផ្ទាល់ខ្លួនរបស់អ្នក ហើយអ្នកអាចពន្យល់គ្រប់បន្ទាត់របស់វាបាន។
- ការពិនិត្យរបស់ kit នៅតែ ✅៖ ផ្នែកបន្ថែមមួយ បន្ថែមលើប្រព័ន្ធរបស់អ្នក វាមិនធ្វើឱ្យផ្នែកណាមួយខូចទេ។
- `tests.py` មាន **តេស្តយ៉ាងហោចណាស់ពីរសម្រាប់វា ដែលអាចធ្លាក់បាន**៖ តេស្តនីមួយៗពិនិត្យចម្លើយមួយ ដែលអ្នកបានគណនាដោយដៃ ហើយយ៉ាងហោចណាស់តេស្តមួយ សាកល្បងចំណុចព្រំដែន ឬធាតុចូលចម្លែកមួយ។

**វិធាន ឬ field ថ្មីមួយ។** *ឧទាហរណ៍:* ព័ត៌មានទំនាក់ទំនង (contact) នៅពេលដែលគេផ្ដល់ឱ្យ ត្រូវតែមានសញ្ញា `"@"` ហើយសារ error និយាយថា *"The contact must be an email address, for example name@example.org."* ឬស្ថានភាព (state) ថ្មីមួយ `returned` សម្រាប់អាហារដែលអង្គការដៃគូផ្ញើត្រឡប់មកវិញ៖ `"picked_up": ["delivered", "returned"]`។ *របៀបសាកល្បងវា:* ធាតុចូលមួយ ដែលវិធានថ្មីរបស់អ្នកបដិសេធ (ហើយដែលវិធានចាស់ធ្លាប់ទទួលយក) និងធាតុចូលមួយទៀត ដែលនៅជាប់ចំណុចព្រំដែន តែនៅម្ខាងទៀត ហើយនៅតែត្រូវបានទទួលយក។ សម្រាប់ស្ថានភាពថ្មី៖ ការប្ដូរស្ថានភាព (move) មួយដែលឥឡូវនេះត្រូវបានអនុញ្ញាត និងមួយទៀតដែលនៅតែមិនត្រូវបានអនុញ្ញាត។ *ប្រយ័ត្ន:* ជួរដេកតេស្តរបស់ kit ផ្ទាល់ មិនមាន field ថ្មីរបស់អ្នកទេ ដូច្នេះ field ថ្មីមួយត្រូវតែជា field **ស្រេចចិត្ត (optional)** (ប្រសិនបើគ្មានតម្លៃ ក៏មិនអីដែរ ឬវាទទួលបានតម្លៃ default)។ ប្រសិនបើអ្នកបន្ថែមវាទៅក្នុង `REQUIRED_FIELDS` ការពិនិត្យ `clean_offer` របស់ kit នឹងធ្លាក់។

**ទិដ្ឋភាពសម្រាប់អ្នកស្ម័គ្រចិត្ត។** *ឧទាហរណ៍:* `VOLUNTEER_FIELDS = ["id", "donor", "food", "portions", "hours_left", "partner"]` និង `volunteer_row(record)` ដែលដំណើរការដូច `public_row`។ ជម្រើស `"4"` រាយបញ្ជីការផ្ដល់ជូនដែលមិនទាន់បញ្ចប់ ដោយការផ្ដល់ជូនបន្ទាន់បំផុតនៅខាងលើ ហើយការផ្ដល់ជូននីមួយៗមានមួយជួរដេកសម្រាប់អ្នកស្ម័គ្រចិត្ត។ តើអ្នកស្ម័គ្រចិត្តត្រូវការអ្វី ដែលសាធារណជនមិនត្រូវឃើញ? តើអ្វីខ្លះដែលអ្នកស្ម័គ្រចិត្តនៅតែមិនត្រូវឃើញ? *របៀបសាកល្បងវា:* `volunteer_row` return field របស់អ្នក ហើយតែ field ទាំងនោះប៉ុណ្ណោះ។ ព័ត៌មានទំនាក់ទំនងមិនស្ថិតនៅក្នុងចំណោមនោះទេ (ប្រសិនបើនោះជាការសម្រេចចិត្តរបស់អ្នក)។ ជម្រើស `"4"` បង្ហាញការផ្ដល់ជូនដែលមិនទាន់បញ្ចប់មួយ ហើយមិនបង្ហាញការផ្ដល់ជូនដែលបានប្រគល់រួចទេ។

**របាយការណ៍សង្ខេបប្រចាំសប្ដាហ៍ ឬក្រាហ្វ។** *ឧទាហរណ៍:* ជម្រើស `"4"` បង្ហាញ *"Offers: 4 · portions offered: 100 · delivered: 18 · rejected: 40 · still open: 42"* ពី function មួយ ដូចជា `summary_text(records)`។ ឬពីប្រវត្តិសប្ដាហ៍ទី 7 របស់អ្នក៖ ចំនួនការផ្ដល់ជូនដែលត្រូវបានបន្ថែម ប្ដូរស្ថានភាព និងបដិសេធ។ ក្រាហ្វមួយត្រូវបានគូរពី function មួយដែល return លេខ៖ ចូរសាកល្បងលេខទាំងនោះ មិនមែនរូបភាពទេ។ *របៀបសាកល្បងវា:* លេខសម្រាប់ record គំរូទាំងបួន ដែលអ្នកគណនាដោយដៃ **មុន** ពេលអ្នក run កូដ និង list ទទេមួយ ដែលត្រូវតែផ្ដល់លេខសូន្យ មិនមែនធ្វើឱ្យកូដគាំងទេ (អត្រានៃក្រុមទទេ គឺ 0.0)។

**ទំព័រសាធារណៈពីសប្ដាហ៍ទី 8។** *ឧទាហរណ៍:* កូដទំព័រសប្ដាហ៍ទី 8 របស់អ្នក ផ្លាស់ទៅនៅក្នុង `make_page(records)` ក្នុង `screen.py`។ វា return ទំព័រនោះជា string តែមួយ ប្រើ `public_row` ពី `report.py` (ចូរ import វា កុំចម្លងវា) ប្រើ `html.escape` ហើយមិនបង្ហាញការផ្ដល់ជូនដែលត្រូវបានបដិសេធ ឬលុបចោលទេ។ *របៀបសាកល្បងវា:* ទំព័រដែលបង្កើតពី record ដែលមានព័ត៌មានទំនាក់ទំនង មិនដែលបង្ហាញព័ត៌មានទំនាក់ទំនងនោះទេ។ ឈ្មោះអាហារដែលមាន `<b>` នៅក្នុងនោះ បង្ហាញជាអត្ថបទធម្មតា (`&lt;b&gt;`)។ ការផ្ដល់ជូនដែលត្រូវបានបដិសេធ មិននៅលើទំព័រទេ។ *តេស្តស្ទង់មើល (canary):* ចូរបន្ថែម ឬដក field មួយនៅក្នុង `PUBLIC_FIELDS`៖ ទំព័ររបស់អ្នកត្រូវតែប្រែប្រួលដែរ។ ប្រសិនបើវាមិនប្រែប្រួលទេ មានន័យថាទំព័រនោះបានចម្លងបញ្ជី field ជំនួសឱ្យការប្រើ `public_row`។

**អេក្រង់មួយដែល AI សរសេរ។** ចូរផ្ដល់កិច្ចសន្យា (contract) មួយដល់ AI មិនមែនគ្រាន់តែប្រាប់បំណងទេ៖

> ចូរសរសេរ file Python មួយឈ្មោះ `screen.py` ដែលមាន function តែមួយ គឺ `make_page(records)`។ វា return ទំព័រ HTML មួយជា string តែមួយ (`str`)។ ចូរបង្ហាញមួយជួរដេក សម្រាប់ការផ្ដល់ជូននីមួយៗដែលមិនទាន់បញ្ចប់ (new, approved ឬ picked_up) ដោយការផ្ដល់ជូនបន្ទាន់បំផុតនៅខាងលើ។ ចូរ import `urgency` ពី `rules.py` និង `most_urgent_first` ពី `report.py` ហើយប្រើវា។ ចូរដាក់ import ទាំងអស់នៅខាងលើគេនៃ file។ កុំសរសេរលេខណាមួយ ដែល function ទាំងពីរនោះប្រើ ម្ដងទៀតឡើយ។ ប្រើតែ standard library របស់ Python ប៉ុណ្ណោះ។ កុំបង្ហាញ field contact ជាដាច់ខាត។

ចូរអានកូដ មុនពេលអ្នក run វា៖ អ្នកបានសរសេរ loop ដដែល និង `html.escape` ដដែលនេះ នៅសប្ដាហ៍ទី 8។ បន្ទាប់មក ចូរធ្វើ **តេស្តស្ទង់មើល (canary test)**៖ ប្ដូរ `URGENT_HOURS` ក្នុង `rules.py` (ទៅ 10 ប្រសិនបើវាតិចជាង 5 ឬទៅ 1 ប្រសិនបើវាស្មើ 5 ឬច្រើនជាងនេះ) Run `bridge.show("screen")` ម្ដងទៀត ហើយមើលថាទំព័រប្រែប្រួលឬទេ។ ប្រសិនបើវាមិនប្រែប្រួលទេ មានន័យថា AI បានចម្លងវិធាន ជំនួសឱ្យការ import វា៖ ចូរសួរវាម្ដងទៀត។ ប្ដូរតម្លៃត្រឡប់ទៅដូចដើមវិញ ហើយសរសេរអ្វីដែលអ្នករកឃើញ ក្នុងកំណត់ត្រាការផ្ទៀងផ្ទាត់របស់អ្នក។ *របៀបសាកល្បងវា:* ការផ្ដល់ជូនដែលបានប្រគល់រួច មិននៅលើទំព័រទេ។ ព័ត៌មានទំនាក់ទំនងមិនដែលលេចឡើងទេ។ ការផ្ដល់ជូនដែលនៅសល់ម៉ោងតិចជាងគេ មកមុនគេ។

### ចូរបង្ហាញថា តេស្តមួយអាចធ្លាក់បាន

«តេស្តទាំងអស់ជាប់» មិនមានន័យអ្វីទេ រហូតដល់អ្នកដឹងថា តេស្តទាំងនោះ **អាច** ធ្លាក់បាន។ ចូរធ្វើឱ្យផ្នែកបន្ថែមរបស់អ្នកខូចដោយចេតនាម្ដង៖ លុប `if` ថ្មីរបស់អ្នក បន្ថែម `"contact"` ទៅក្នុងបញ្ជី field របស់អ្នក ឬប្ដូរលេខមួយ។ រក្សាទុក Run `bridge.check("all", folder="my_foodbridge")` ហើយមើល ❌។ បន្ទាប់មក ដាក់កូដត្រឡប់មកវិញ រក្សាទុក ហើយ Run ម្ដងទៀត៖ ✅។ លទ្ធផលទាំងពីរ ត្រូវកត់ក្នុងកំណត់ត្រាការផ្ទៀងផ្ទាត់របស់អ្នក។

- *«urgent គួររួមបញ្ចូលមួយម៉ោងទៀត លើសពីឥឡូវ។»* → `URGENT_HOURS` នៅក្នុង `rules.py`៖ ពី 3 ទៅ 4៖ F004 ប្ដូរពី soon (ឆាប់ៗ) ទៅជា urgent (បន្ទាន់)។ តេស្តរបស់អ្នក ដែលសរសេរដោយប្រើតម្លៃថេរ នៅតែជាប់។ ប្រសិនបើតេស្តមួយធ្លាក់ វាមានលេខដែលសរសេរផ្ទាល់នៅក្នុងនោះ (សប្ដាហ៍ទី 4)៖ តើបន្ទាត់ណា?
